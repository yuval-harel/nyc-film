NYC Film Aggregator

Process, Architecture, and Implementation Strategy

Conceptualizing the Tool PHASE 01

Currently, cultural data in New York City is highly fragmented. To find a specific screening, users must navigate dozens of disparate, siloed cinema websites. This project acts as a functional critique of that fragmentation, unified through a singular, accessible interface.

The goal is not to build a static mockup, but a production-quality utility. The design relies on strict visual hierarchy, utilizing high-density typography and clear layout containers rather than excessive UI decoration. The interface must communicate complex overlapping states (like Calendar conflicts and Letterboxd watchlists) simultaneously without overwhelming the user.

Interaction & Prototyping PHASE 02

Before writing the frontend code, the user flow and logical constraints are mapped out. This involves establishing variables for time-window filtering and creating variant instances for screening states.

  • Boolean & String Variables: Defining the logic for when a film should display a "Calendar Conflict" (red) vs. "Watchlist Match" (green).
  • Variant Instance Swapping: Designing hovercards and tooltips for exact ticket links and venue details.
  • Data Structures: Planning how the raw JSON from the backend will be parsed into styled, responsive HTML components.

Data Normalization & Architecture PHASE 03

The core of this application is its normalized PostgreSQL database. Because different venues format titles and addresses differently, a robust deduplication system is required. Here is the structural logic for the primary entities:

Entity Role in System Key Attributes Normalization Strategy
Venue Physical screening location Canonical Name, Place ID, Coordinates Mapped via aliases to prevent duplicates (e.g., "Alamo Brooklyn" = "Alamo Drafthouse").
Film The canonical movie identity Title, Year, IMDb ID, Runtime Matched using IMDb bulk data and precise string filtering to prevent false merges.
Screening The actual time and place Start Time, End Time, Format Unique deterministic fingerprint (Venue + Film + Start + Source) to prevent duplicate ingestions.

The Ingestion Pipeline PHASE 04

The application employs a Source-Adapter pattern. Instead of writing one giant, fragile script, each cinema has an isolated class that fetches its schedule and returns a normalized payload. We use DOM parsing for server-rendered HTML and automated browsers only when strictly necessary.

// Example Adapter Architecture class SourceAdapter { sourceId: string; sourceName: string; // Extracted and cleaned string data protected cleanString(str: string): string { return str.toLowerCase().replace(/[^\w\s]/g, '').trim(); } // Abstract method implemented by each specific cinema abstract fetchSchedule(date: string): Promise<NormalizedScreening[]>; }

Full-Stack Implementation PHASE 05

Frontend

  • Next.js (App Router): For server-side rendering and routing.
  • React & TypeScript: Ensuring type safety across complex data states.
  • Tailwind CSS: For rapid styling, focusing on density and editorial typography.

Backend

  • PostgreSQL: Persistent relational database for all scraped schedules.
  • Prisma ORM: Schema management and typed database queries.
  • Node.js Workers: Scheduled cron jobs for executing scraper adapters.

Integrations

  • Google Places API: Resolving precise theater locations and ratings.
  • Google Calendar OAuth: Interval-overlap logic for schedule conflicts.
  • IMDb Datasets: Processing official TSVs for non-commercial metadata.
